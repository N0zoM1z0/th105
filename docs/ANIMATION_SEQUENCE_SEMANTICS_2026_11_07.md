# Animation action map and sequence blocks

The selected character constructor allocates a checked `std::map<int, AnimationSequenceBlock *>` and stores its pointer at `+0x160`. The sequence-selection view now exposes that map type directly rather than storing a synthetic tree pointer and casting it to a map at the selection call. Its key is the action ID; its mapped value is the first sequence block. Blocks carry a frame range and links to previous/next blocks. The original class spelling and complete ownership hierarchy remain unproved.

The effect resource loader independently shows why action IDs should not be assumed to own unique blocks: normal keys register blocks, `-2` appends a linked continuation, and `-1` entries are resolved later as aliases. That is evidence for the effect resource path, not a claim that every loader uses identical file rules. EFZ's recovered implementation has separate parallel visual-pattern and battle-frame arrays; its `sequence` therefore is not assumed to be the same physical structure or timing unit as TH105's linked block.

The selection routine now calls the typed map directly. The reset routine still uses its narrow checked-tree view: a direct checked-map iterator implementation was tried, but changed the complete emitted body and could not yet be reflected safely in the current origin census while unrelated census validation failures remain unresolved. This is a recorded limitation, not evidence against that more natural source. Ten sequence virtuals and 23 other already-exact functions in 13 directly including units compared exactly after the selected type change; the other selected roots were already nonexact. No new exact credit is claimed.

## Shared visual-frame fields

The `FrameData` owner now names its eight stored 16-bit fields by their independently observed visual/animation roles: pivot X/Y, duration, texture index, and texture rectangle X/Y/width/height. The suffix `bits` deliberately preserves the existing unsigned storage representation; the render and animation views interpret these same 16-bit patterns as signed values. This is not a claim that the original declaration used unsigned or signed types. The effect loader writes these fields directly, and the fighter PAT loader now does too instead of accessing them through `pat_member<short>` at literal byte offsets. The effect loader remains 2,528/2,528 exact. The nonexact fighter loader emitted an identical candidate hash before and after, still first differing at +866.

Seven affected units were checked: all 11 existing exact entries in them still compare exactly. Eight generated PAT/effect origin rules were individually rebuilt and passed. The prior full-census issues remain separate and no newly exact claim is made.
